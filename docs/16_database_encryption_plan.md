# Database encryption plan

Status: code implemented; technical phone encryption check passed; user data visibility check pending, 14 September 2026.

This document locks the planned approach for encrypting the Android APK's local SQLite database before any real client pilot. It is based on the current codebase, where all production database access goes through `AppDatabase.open()` and the app stores data in `ansvk_outreach.db` under Android app-private storage.

## Decision

Use SQLCipher through the Flutter package `sqflite_sqlcipher`, with a database passphrase stored in Android-backed secure storage through `flutter_secure_storage`.

This is the lowest-change path for the current APK because:

- the app already uses the `sqflite` API shape;
- `sqflite_sqlcipher` keeps the same general API and adds a `password` argument when opening the database;
- production database opening is centralized in `lib/database/app_database.dart`;
- tests can continue to use `sqflite_common_ffi` for ordinary schema/repository behavior while Android encryption is verified through device/build tests.

## Source checks

- Flutter's own SQLite recipe describes the current `sqflite` style used by the APK: get a database path, then open the database with `openDatabase()`.
- `sqflite_sqlcipher` describes itself as a `sqflite` fork using SQLCipher on Android/iOS/macOS. Its documented API keeps `openDatabase()` and adds an optional `password` parameter.
- `sqflite_sqlcipher` says Android release builds need a ProGuard rule to keep `net.sqlcipher` classes.
- `sqlcipher_flutter_libs` should not be selected for this project because its current documentation says the package does not do anything and was only for older `sqlite3` package usage.
- `flutter_secure_storage` documents Android secure value storage and warns that Android backup can affect secure-storage keys. The APK already sets `android:allowBackup="false"` in `AndroidManifest.xml`.

- Flutter SQLite persistence: https://docs.flutter.dev/cookbook/persistence/sqlite
- sqflite_sqlcipher: https://pub.dev/packages/sqflite_sqlcipher
- sqlcipher_flutter_libs current documentation: https://pub.dev/documentation/sqlcipher_flutter_libs/latest/sqlcipher_flutter_libs/

## Key rule

The database encryption passphrase must be generated by the app and stored in secure storage. It must not be derived directly from the worker's app password.

Reason: workers can forget or change app passwords. The current pilot decision says there is no password recovery or bypass. Tying the database key directly to the worker password would make future password-change/recovery design more fragile and could make locked records unrecoverable even when the phone and app storage are otherwise intact.

The generated passphrase should:

- be random;
- be created once on first encrypted database setup;
- stay on the same phone;
- be deleted only when app data is cleared/uninstalled;
- never be included in sync payloads, logs, audit tables or dashboard records.

## Migration rule for the current development APK

The current database file is unencrypted. For this development phase, the implementation should support a safe one-time migration:

1. Detect whether the existing `ansvk_outreach.db` can be opened as an encrypted SQLCipher database with the secure-storage passphrase.
2. If encrypted open succeeds, continue normally.
3. If encrypted open fails, check whether the existing file is a plain SQLite development database.
4. If it is a valid plain database, copy its content into a new encrypted database.
5. Keep a temporary backup during migration.
6. Replace the old database only after the encrypted database opens and passes a basic integrity check.
7. Do not silently delete data after a failed migration.

This migration is for development data and pilot preparation. It is not a dashboard sync or password recovery feature.

## Android implementation notes

Implemented code changes:

- Production `AppDatabase.open()` uses `sqflite_sqlcipher` when tests do not inject a database factory.
- Tests continue to inject `sqflite_common_ffi`; repository/schema code uses `sqflite_common` types.
- The plain `sqflite` app dependency was removed so Android does not package the ordinary sqflite plugin directly.
- `flutter_secure_storage` stores the generated local database passphrase in namespace `ansvk_outreach_database_key`.
- `DatabaseKeyStore` creates/reads the local database passphrase.
- Android ProGuard keep rule was added:

```proguard
-keep class net.sqlcipher.** { *; }
```

- Keep `android:allowBackup="false"`.

## Risks and limits

- Encryption protects the database file at rest, but it does not replace app lock, phone passcode, worker training or future dashboard sync.
- If the secure-storage key is lost because app data is cleared, uninstalled, or damaged, the encrypted database may become unreadable.
- This does not create password recovery.
- This does not make the debug APK ready for real client use by itself. Production signing, final pilot checks and real sync decisions still remain.
